# System reminders V1

## Ingest

`POST /reminders` uses the existing gateway-token, API-key and Relay authentication.
iOS sends the following through its unified API client to
`/api/message/messageBridge/send`, with `path: "reminders"` and a JSON-string `payload`.

```json
{
  "schemaVersion": 1,
  "sourceId": "opaque-installation-account-id",
  "collectedAt": "2026-10-22T09:00:00.123+08:00",
  "items": [{
    "id": "system-calendar-item-id",
    "title": "Call the supplier",
    "listId": "system-list-id",
    "listName": "Work",
    "due": {"date": "2026-10-23", "time": null, "timeZone": null},
    "isCompleted": false,
    "completedAt": null,
    "priority": 1,
    "isRecurring": false,
    "notes": "Confirm delivery time",
    "url": null,
    "createdAt": "2026-10-20T08:00:00.000+08:00",
    "modifiedAt": "2026-10-22T08:00:00.000+08:00"
  }]
}
```

Each upload is a complete snapshot of every reminder currently visible to that
source, including completed and undated reminders. No time window or future
recurrence expansion is applied. Distinct system IDs remain distinct even when
titles are identical. This is a read-only integration; it does not change system reminders.

- `sourceId` is generated by the app, stable across Agent/API-key changes and
  separate across installations, accounts and environments. iOS excludes its
  local identifier files from backup to avoid restoring a shared source ID onto
  another device. Reinstallation creates a new source; V1 does not merge sources.
- `collectedAt` is frozen before the system query. Timestamps include an offset;
  `createdAt`, `modifiedAt` and `completedAt` may be null.
- `due: null` means no due date. A null `due.time` means date only; a null
  `due.timeZone` preserves floating semantics. Times use `HH:mm:ss`. Zone names
  are IANA identifiers or Foundation fixed-offset identifiers such as `GMT+0530`.
- `priority` preserves EventKit's integer 0–9; `isRecurring` is only a boolean.
  Recurrence rules, alarms, start dates and locations are outside V1.
- Full reminders permission is independent of calendar permission. iOS requests
  it only from an explicit tap in asset settings, with
  `NSRemindersFullAccessUsageDescription`. Foreground and debounced
  `EKEventStoreChanged` refreshes consume existing access. They do not promise
  continuous background execution.
- Denied/revoked access, nil fetch results, malformed records and oversize payloads
  fail the whole batch. They never become a successful empty snapshot.
- Limits: 20,000 items, 16 MiB request, 64 KiB per stored record. The aggregate
  mirror is bounded to 64 MiB of JSONL and 32 MiB of index; the private transaction
  is bounded to 128 MiB. iOS rejects oversize snapshots without truncating them.

Only this `sourceId` is replaced. Absent IDs leave its current mirror; this does
not prove the user deleted them. Other sources are preserved. A snapshot whose
collection time is older than or equal to the accepted watermark is acknowledged
with `applied: false, ingested: 0`. The response always includes `ok`, `applied`,
`ingested` and the content `revision`.

## Files

Under the current profile:

```text
reminders/
  active.jsonl
  completed/YYYY-MM-DD.jsonl
  completed/undated.jsonl
  index.json
  state.json
  README.md
```

JSONL rows contain the full item plus `sourceId` and `recordId`. `recordId` is an
opaque SHA-256 identifier derived from `[sourceId, id]`. Completed partitions use
the date written in `completedAt`, including its offset; no completion time uses
`undated`. Completing, reopening and changing completion dates moves the record.
These files describe current state, not an immutable operation history.

`index.json` has `schemaVersion`, `revision` and `items`. Each entry contains
`sourceId`, `recordId`, `id`, `title`, `listId`, `listName`, `due`, `isCompleted`,
`completedAt`, `priority`, `isRecurring` and a relative `file` location. Notes,
URL, creation/modification timestamps stay in JSONL. There are no byte offsets,
line numbers or separately persisted sort arrays. A missing index is rebuilt
from current partitions; a malformed index fails closed. Rebuilding also rejects
records without source watermarks, or persisted watermarks with no partitions,
rather than serving an inconsistent or falsely empty snapshot.

`state.json` contains `schemaVersion` and `sources`, a map from source ID to
`{ "lastCollectedAt": "..." }`. A content-identical sync only updates that
watermark. Full-record changes, including notes, change the content revision.

All daemon reads/writes share the storage lock. A bounded `.pending.json` redo
journal is written before replacing live partitions, index and state. Interrupted
replacements finish before any API read or later upload proceeds. This file is
temporary recovery metadata, not reminder history. On Unix, partition deletions
are directory-synced before removing the journal; directory-sync failures fail
the write. Windows retains journal recovery for process interruptions without
Unix directory-fsync guarantees. Agents should query the API
or CLI instead of reading raw files during a replacement.

## Queries

`GET /assets/reminders` supports:

| Parameter | Meaning |
| --- | --- |
| `status` | `incomplete` (default), `completed`, `all` |
| `sourceId`, `listId` | Optional exact match |
| `dueFrom`, `dueTo` | Inclusive due-date bounds, `YYYY-MM-DD` |
| `completedFrom`, `completedTo` | Inclusive completion-date bounds |
| `limit` | 50 default, 1–100 |
| `cursor` | Opaque continuation returned by the prior page |

Date filters exclude items without the relevant date. Incomplete reminders sort
by due date and wall-clock time ascending, date-only before timed on the same day,
undated last. Completed reminders sort by completion instant descending, unknown
last. `all` places incomplete first. `recordId` breaks ties deterministically.

The response uses `ok`, `items`, `nextCursor`, `warnings`, with `revision` and
`sources` sync metadata. Each item has the standard asset `recordId`,
`storageDate: null`, `status: "ok"`, `data` and `truncatedFields: []` fields.
List `data` is the index summary without `file`. Pages stop at both the item limit
and 256 KiB response limit. Only a null cursor means the end.

`GET /assets/reminders/{recordId}` returns the same envelope with exactly one
full item, including notes/URL/system timestamps. An optional `revision` must
match the list revision. An absent reminder returns 404 `REMINDER_NOT_FOUND`.
An indexed partition that cannot be read is a source error, not an empty result.

Signed cursors bind profile, filters, fixed sort order, revision and next result
position. Query mismatch is 400; wrong profile is 403; changed revision, restart
or expiry is 410 and requires restarting the list. Identical content resynced at
a newer time does not invalidate cursors. Reads cover every source in the current
single-owner profile, regardless of the calling API-key label.
Filters that cannot fit the 4096-byte signed cursor budget after JSON/base64
encoding are rejected on the first request, instead of returning an unusable cursor.

Both routes also accept the existing bounded read-only POST envelope
`{"method":"GET","body":null}` for messageBridge. Capabilities are `reminders`
and `assets.reminders.read.v1`.

Lists read/filter the compact index, then sort matches in memory; they do not
scan full JSONL or return notes. This is O(N) filtering and O(M log M) sorting,
not a database index with constant-time lookups. Detail scans the single indexed
partition. This keeps V1 simple while avoiding loading full notes into Agent context.

## Agent CLI

The CLI uses the same daemon API, so cursor, filter and consistency semantics
match the client. The daemon must already be running.

```sh
yoooclaw reminders list --format json
yoooclaw reminders list --status all --due-to 2026-10-23 --limit 50 --format json
yoooclaw reminders list --cursor '<nextCursor>' --format json
yoooclaw reminders get '<recordId>' --revision '<revision>' --format json
```

Flags `--source-id`, `--list-id`, `--due-from`, `--due-to`, `--completed-from` and
`--completed-to` map to their corresponding query parameters. Agent context
discovery lives in the shipped `yoooclaw-context-query` skill's reminders reference.
Read summaries first, fetch only relevant details, and use sync timestamps when
describing freshness. This mirror is separate from the cloud `yoooclaw todo` service.

## Memory consumption

`sync scan/next --source reminders` reads the daemon's revision-consistent asset
API and uses an independent per-profile memory checkpoint. No date flags means
all unconsumed current records. Explicit dates select modifiedAt, then createdAt,
then source lastCollectedAt, never the due date. `next` freezes up to 20 full
records within the existing soft 64 KB batch budget, unfinished first. Identity
is recordId and version is a hash of full record content; a newer collection
watermark alone does not cause reconsumption.

`sync commit --source reminders --token <token>` acknowledges only the frozen
versions and preserves previous data for reconciliation. A repeated confirmation
of the last token is idempotent. A concurrent upstream revision remains pending.
Missing records produce no deletion inference or event. Ordinary list/get queries
do not affect this checkpoint. The memory skill allows each source independently
up to three nonempty batches per user run; the CLI does not infer user-run boundaries.
