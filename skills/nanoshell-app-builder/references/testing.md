# 自动验收

先将需求变成 `acceptance.md` 中逐项编号的观察结果，再编写 `tests/<name>.mjs`。场景导出 `default async function ({page, assert})`，返回已断言的需求编号数组；返回数组前每项都应有会失败的断言。通过截图、屏幕像素区域或可观察状态判断行为，避免只检查源码字样或点击成功。

```bash
node "$SKILL/scripts/test_app.mjs" --project "$PROJECT" --name "$NAME" --scenario "tests/$NAME.mjs"
```

脚本提供已运行应用的 Playwright `page` 和 Node 严格断言 `assert`。页面 `#screen` 是 240×120 画布，Enter/空格为 OK，Escape 为 BACK。场景结束时保持 App 正在运行，通用测试随后验证 BACK 退出和再次启动。需要复现随机玩法时采用可控输入/随机种子测试策略，并记录其与正常运行的差别。

例如计数器：在按 OK 前后读取数字区域像素或截图，断言变化；长按后断言多次计数；重开后断言持久化结果。对飞行游戏还应覆盖下落、扑腾、越障得分、碰撞结束、重开。纯画面变化只证明变化，不能代替分数正确、碰撞正确等断言。

## 通用检查及产物

脚本验证：包大小与 manifest、NSP1 头及载荷长度、Wasm 可编译、`start` 导出、`ns` 导入白名单、经 HTTP 读取的 `/dist/` 安装包与测试文件字节一致、页面跨源隔离、连续帧、非空白画面、OK 短按和长按的共享输入消费、BACK 正常退出、再次启动、页面/Worker 错误。

产物位于 `qa/<name>/`：`report.json`、启动/交互截图。报告 `status=passed` 只在全部断言通过时产生；缺依赖、超时、无专用场景均不能当作通过。连续帧与输入消费是冒烟检查，不能证明 guest 已按业务含义处理输入。查看截图后再向用户提供试玩。

硬件交互场景使用 [设备交互与验收](interactions.md) 的模拟入口和调用记录，断言业务触发条件、参数及退出清理；报告保存调用证据。

能力边界：Web Host 对灯效、BLE、震动等作模拟；测试不证明真机 Wasm3 内存预算、帧率、无线通信或断电持久化符合要求。将实际依赖的这些能力列为待真机验收项。
